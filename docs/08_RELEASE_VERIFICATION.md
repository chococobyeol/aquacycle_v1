# 08. 배포 검증 기록

> 갱신일: 2026-08-05
> 대상: 현재 작업본의 미션 1~7 배포 게이트, 미션 8 개발 검증 대기,
> 실험실, 생태·물질 순환 및 관찰 기능

이 문서는 과거 어느 시점의 통과 개수만 남기는 기록이 아니라, 현재 배포본에서
무엇을 실제 문제로 판정하는지와 같은 검사를 다시 실행하는 방법을 함께 고정한다.

> **현재 배포 판정:** 미션 1~7의 장기 생태 게이트와 데스크톱 Renderer
> 안정성 게이트를 분리한다. 큰물벼룩 탈피–육방과 체리새우 난소 주기를
> 적용한 두 미션 7 fixture는 제한시간·미션 성공 문자열을 사용하지 않은
> 장기 생태 기준으로 통과했다. 그러나 2026-07-27 실제 Electron 장시간
> 실행에서 Renderer 메모리 종료가 다시 확인됐으므로, 아래 수정은 새
> Renderer의 실제 장시간 실행을 통과하기 전까지 데스크톱 안정성
> **재검증 대기**로 기록한다.

## 1. 배포 전 일괄 검증

```text
npm run verify:release
```

이 명령은 다음 순서로 실행된다.

1. TypeScript 정적 검사
2. 현재 저장소에 등록된 전체 자동 회귀를 단일 작업자에서 실행
3. 미션 6 생산자·미생물·체리새우계의 낮·밤 50주기 확장 검증
4. 미션 7 최소 정상 배치와 풀스톡 배치의 장기 생태 행렬 검증

단일 작업자는 모델을 느슨하게 만드는 설정이 아니다. 서로 독립적인 장시간
시뮬레이션들이 같은 CPU를 동시에 차지해 성능 제한시간만 넘기는 거짓 실패를
막는다. 64배속 계산량과 Worker 성능 계약은 각각의 전용 시험에서 그대로 검사한다.

생애·먹이망 변경 중 미션 1~7 누적 장기 게이트만 다시 실행할 때는 다음
명령을 사용한다.

```text
npm run verify:ecology-long-run
```

## 2. 생태 검증 작성 규칙

- 과제 해법 검증은 목록에서 항목을 고르고 수조에 놓는 공개 명령만 사용한다.
- 정상 플레이에서 만들 수 없는 방식으로 모든 셀의 생체량을 직접 채우지 않는다.
- 광원 출력 숫자가 크다는 이유만으로 생산성이 높다고 가정하지 않는다. 종별
  광반응을 지난 실제 생산량·생체량·누적 섭식량을 관찰한다.
- 순간 개체 수 하나로 숨은 수용량을 추정하지 않는다. 출생 기록, 실제 섭식,
  세대교체와 기술 안전선이 생태 판정에 개입하지 않는지를 나눠 확인한다.
- 미션의 성공·실패, 제한시간, 목표 유지시간은 UI 과제 회귀에만 사용한다.
  장기 생태 판정은 성공하지 못한 실행도 끝까지 계속 돌려 같은 기준으로
  평가한다.
- 새우 개체군의 멸종과 탄소·질소·산소 등가 장부 누출은 별개로 판정한다.
- 미션 해법은 특정 장식 배치를 강요하지 않되, 공급된 먹이를 볼 수 있는 위치에
  배치하는 것처럼 플레이어가 화면에서 판단할 수 있는 행동으로 구성한다.

단위 수식 시험은 필요한 상태 하나만 고립하기 위해 내부 값을 설정할 수 있다.
그러나 그 결과를 그대로 과제의 플레이 가능성이나 전체 생태 평형의 증거로 쓰지
않는다.

### 2.1 미션 1~7 장기 생태 수락 행렬

미션 번호는 어떤 생태 구성요소가 처음 등장하는지 고르는 fixture 이름일
뿐이다. 미션 목표 문구를 검사하지 않고, 해당 시점까지 등장한 생물이 공개
배치 명령으로 만든 수조에서 장기적으로 기능하는지를 누적 검증한다.

| 범위 | 장기 판정 |
|---|---|
| 미션 1 | 붓뚜껑말 생체량이 유한·비음수이고 실제 광량에 반응하며, 장기 실행 뒤 0 또는 비유한값으로 무너지지 않음 |
| 미션 2 | 규조류에 같은 수치 안전성을 적용하고, 저광·적정광의 상대 반응이 유지됨 |
| 미션 3 | 구조물과 바닥의 붓뚜껑말 군락이 전체 자원 한도 안에서 유지되고 셀 수를 늘렸다고 물질이 무한 생성되지 않음 |
| 미션 4 | 두 부착조류와 체리새우가 함께 남고, 창시자 노화 뒤 출생 자손의 성숙·번식이 이어지며 후반 표본의 개체 수가 0이 아님 |
| 미션 5 | 미션 4 조건에 두 균 기능군, 유기물–암모니아성 노폐물–영양염 순환, 안전한 산소와 탄소·질소·산소 등가 보존을 추가 |
| 미션 6 | 미션 5 조건에 낮·밤 생산자 호흡 전환, 나사말 성장·야간 호흡·런너 자손 생존, 3세대 이상 새우 8마리를 포함한 전체 15마리의 3주기 연속 유지와 별도 장기 개체군 범위를 추가 |
| 미션 7 | 미션 6 조건에 식물플랑크톤의 고갈 뒤 회복, 큰물벼룩의 탈피·출생·성숙·창시자 교체와 살아 있는 후속 세대를 추가 |

개체군에는 특정 최종 마릿수나 평균값을 정답으로 두지 않는다. 종과 다음
먹이망 단계에 맞춘 후반 최저값, 후속 세대의 출생·성숙, 자원 고갈 뒤
회복과 비정상 폭증 경보를 함께 본다. 현재 미션 7 큰물벼룩 수락선은 후반
최저 `15마리`, 평균 `30마리`, 최종 `20마리` 이상이며 체리새우는 후반
모든 표본에서 `4마리` 이상이다. `19`와 `20`처럼 한 표본의 경계 차이를
생태식 보정 근거로 삼지 않되, 마지막 순간에만 수가 늘고 후반 출생·성숙이
끊긴 실행도 통과시키지 않는다.

2026-07-27 작업본은 별도 검사의 합산이 아니라 단일 작업자 전체 회귀 한
번에서 `60`파일의 `346/346`을 연속 통과했다. 새 먹이·교미 단서가 없는
수조는 비어 있는 단서장을 갱신하지 않으며, 전체 장주기 직후의 성능 검사도
광 경로 재사용 `4.42초`, 고배속 개체 모션 `15.70초`로 통과했다. 이 시간은
생태 합격식이 아니라 알고리즘 퇴행 경보다.

이번 장기 정지 수정 뒤에도 한 번의 `npm run verify:release`에서 정적 검사,
`67`파일 `383/383`, 50주기 `14/14`, 미션 7 두 fixture `13/13`씩을
연속 통과했다. 이는 생태·전송·표시 코드의 자동 회귀 근거이며 아래 실제
Electron soak 대기 판정을 바꾸지는 않는다. 최종 리뷰에서 사체 dirty
판정과 모션 staging 회귀 2개를 추가한 뒤에는 같은 전체 단일 작업자
회귀를 다시 실행해 `385/385`를 통과했다.

같은 날 사용자가 실행해 둔 개발용 Electron의 미션 7을 `×64`로
`700:00`까지 진행한 상태에서 Renderer가 다시 종료됐다. 종료 직전 생태는
물벼룩 약 `202`, 새우 `55`, 남은 사체 `29`, 식물플랑크톤 약 `17`이었다.
누적 출생 `6,595`, 사망 `6,345` 중 노화 `6,001`, 굶주림 `344`, 기타
사망 `0`이므로 수조 계산이 절멸·정지한 상태가 아니라 큰 세대교체로 사체가
몰린 상태였다.

직접 종료 원인은 Renderer 프로세스의 Chromium PartitionAlloc 메모리
고갈이다. 가장 최근 같은 사용자 창의 PID `10743`은 `12:15`의 전용
메모리 `198.6MB`에서 `12:48`의 `5,969.8MB`까지 거의 선형으로 증가했다.
그 뒤 약 `5.9GB`와 메인 창 JS heap `60~90MB` 부근에서 swap thrash를
계속하다 `13:37`에 `renderer process gone: reason=crashed exitCode=5`로
종료됐다. `sample`에서는 Renderer main thread와 Dedicated Worker가 모두
실행 가능한 CPU 고부하 상태였고, `vmmap`은 physical footprint 약 `5.8GB`,
swap 약 `5.5GB`, 수만 개의 약 `2MB` 영역을 기록했다.

2026-07-27에 남은 여섯 Renderer 진단 보고서를 Electron `41.7.1` 공식
심볼로 확인한 공통 종료 스택은
`partition_alloc::internal::OnNoMemoryInternal → OnNoMemory →
blink::PartitionsOutOfMemoryUsing1G → Partitions::HandleOutOfMemory →
PartitionRoot::OutOfMemory`다. macOS의 `Memory Tag 253`은 Chromium
PartitionAlloc이고 `255`가 V8 heap이다. 각 보고서에서 그 다음 정상 할당
호출자가 timer, 접근성 IPC, debugger, script decoder 등으로 달랐던 것은
그 기능들이 각각 누수 원인이라는 뜻이 아니라, 이미 고갈된 allocator에서
마지막으로 실패한 할당 지점이 달랐다는 뜻이다. 종료 뒤 미션 목록이 보인
것은 복구된 같은 시뮬레이션이 아니라 Electron이 새 Renderer를 불러온
결과다.

진단 해석은 Chromium의
[Memory Tag 정의](https://chromium.googlesource.com/chromium/src/+/f673a07393abb644b28575e8c8cac9052a44183e/base/allocator/partition_allocator/src/partition_alloc/page_allocator.h),
[PartitionAlloc 설계](https://chromium.googlesource.com/chromium/src/+/56c267d43381c48f5fc1d1acf43550e2cd3e759a/base/allocator/partition_allocator/PartitionAlloc.md),
[Renderer idle-time 회수 구현](https://chromium.googlesource.com/chromium/src/+/refs/heads/main/base/allocator/partition_alloc_support.cc)을
기준으로 했다. Chromium 구현도 주기적 회수를 idle task에서 실행한다고
명시하므로, 영구 `0ms` 실행열을 끊는 것은 단순한 속도 완화가 아니라
allocator가 비어 있는 span과 thread cache를 회수할 기회를 보장하는
필수 조건이다.

확인된 주요 증가 경로와 함께 발견한 정합성 결함은 다음처럼 분리한다.

- `stepGrowth`가 해당 종의 생체량이 없는 셀에서도 나사말 잎·수관 기하를
  계산하고 성장 전후 객체·모집 목록을 반복 생성했다.
- 식물플랑크톤과 부착조류 Canvas texture를 전체 스냅샷마다 다시 업로드했다.
- 수질 지도가 꺼져 있어도 생물막 합계 변화 때문에 보이지 않는 분석 canvas가
  약 1Hz로 다시 그려지고 texture upload까지 실행됐다.
- 집단 사망 때 생체 리그가 반환되기 전에 활동 사체 리그가 모두 추가되고,
  반환 풀도 과거 최고 개체 수를 크게 유지했다.
- 단일 공유 payload를 읽는 중 Worker가 같은 바이트를 덮을 수 있었고,
  고정 payload 초과는 UI 갱신을 조용히 중단했다. 이는 crash의 유일
  원인으로 단정하지 않지만 별도 정합성·정지 위험이다.
- `×64`에서 한 `1/120초` quantum의 계산 시간이 `8.33ms` 이상이면, 기존
  스케줄러는 그 계산 시간 자체를 다음 pending 시간에 다시 더했다. 그 뒤
  pending이 줄지 않은 채 `setTimeout(0)`을 영구 반복해 Worker 명령·motion
  발행과 Chromium의 idle-time 메모리 회수 기회를 함께 고갈시켰다.

수정 뒤 같은 고부하 fixture의 전용 cadence 측정은 한 quantum 평균
`6.13ms`, p95 `12.14ms`, 최대 `13.61ms`였다. p95가 실제 벽시계 예산
`8.33ms`를 넘으므로 이 분기는 이론상의 예외가 아니며, 기존 방식으로는
일부 구간에서 부채를 해소할 수 없었다. 새 스케줄러는 정상 구간의
`1/120초` 적분을 유지하되 최대 네 번까지만 즉시 따라잡고, 과부하가
확정되면 달성 불가능한 벽시계 부채를 버린 뒤 최소 `4ms` 양보한다. 느린
callback `4,000회`와 최대 backlog callback `2,000회` 회귀에서 영구
`0ms` 실행열이 생기지 않음을 별도로 확인했다.

현재 수정은 빈 생산자 셀을 생리·수관 계산 전에 건너뛰고, 성장 작업장과
사체 aging을 제자리 재사용한다. 식물플랑크톤·부착조류는 정적 texture와
Sprite transform만 갱신하며, 활동 사체 트리는 종별 표시 상한을 사용한다.
꺼진 분석 지도는 raster surface 생성 전 즉시 종료한다. 동물 좌표·수질
표본과 구조물 표면 좌표, 종별 생태 인구 배열을 재사용하고 30Hz motion은
숫자 채널에 필요한 필드만 계산한다. 정착한 사체는 새 전체 스냅샷이 올
때까지 매 RAF 자세 갱신을 건너뛴다.
전체 스냅샷 채널은 세 고정 슬롯과 읽기 슬롯 claim·슬롯별 길이를 사용하고,
용량 초과 시 최신 대형 상태를 최대 1Hz로 합쳐 일반 메시지로 복구하고 마지막
상태도 trailing publish한다. Worker는 과부하가 확인되면 달성 불가능한
벽시계 부채를 버리고 양의 지연으로 반드시 양보한다. 복원 사체 값과 물벼룩
최대 표시 배율, 표시 사체와 선택 목록도 같은 경계로 정규화했다.
생체량·먹이·섭식·번식·수명·사망과 사체 물질 장부는 바꾸지 않았다.

V8 allocation sampling에서는 기존 100 tick 기준 `shrimpSurfaceContactPoint`
약 `689MB`, `algaePhysiology` 약 `452MB`, `cellWorldPoint` 약 `358MB`,
`applyBiofilmReactions` 약 `340MB`, `stepGrowth` 약 `296MB`,
`stepBiofilmDispersal` 약 `117MB`의 짧은 수명 할당이 확인됐다. 좌표 캐시와
typed 작업장 적용 뒤 `cellWorldPoint`와 `shrimpSurfaceContactPoint`는 상위
할당 목록에서 사라졌고, 100 tick 표본 종료 시 Node RSS 약 `247MB`, heap
사용 약 `37MB`, ArrayBuffer 약 `27MB`였다. sampling profiler는 최적화를
방해하고 수치 연산의 boxed 값까지 호출자에 귀속하므로 절댓값을 합격 기준으로
사용하지 않는다. 이 비교는 지배 경로를 찾는 근거이지 실제 Electron 장시간
합격을 대신하지 않는다. Node 기반 생태 검증의 RSS나 메인 창
`performance.memory`만으로도 Renderer 합격을 선언하지 않는다.

### 4.1 장시간 Renderer 안정성 게이트

다음 실제 Electron 실행은 자동 생태 회귀와 별도로 모두 만족해야 한다.

- 새 Renderer PID에서 미션 7 `×64`를 최소 `45,000` 시뮬레이션초까지
  진행해 기존 `42,000초` 실패 지점을 넘긴다.
- 워밍업 뒤 1분 간격 `private` 메모리가 계속 직선·단조 증가하지 않는다.
  보수적 경보선은 연속 15분 증가량 `256MB`다.
- 같은 Renderer PID가 유지되고 `renderer process gone`이 없어야 한다.
- 진행 뒤 메뉴·일시정지·개체/사체 선택·관찰 패널이 즉시 반응해야 한다.
- 사체는 종별 표시 수명이 지나면 사라지고, 동시 사망 때 화면 트리는 종별
  표시 상한을 넘지 않아야 한다.
- 메인 창 heap, Node 생태 실행과 실제 Renderer soak는 서로 대체하지 않는다.

미션 7 장주기는 다음 명령으로 두 고정 fixture를 차례로 재현한다. 모델 수치
보정 중에는 `verify:mission-7-long-run:minimal`과
`verify:mission-7-long-run:full-stock`을 따로 실행해 어느 조건에서
실패했는지 분리한다.

```text
npm run verify:mission-7-matrix
```

두 fixture는 다음과 같다.

| fixture | 배치 | 놓치면 안 되는 문제 |
|---|---|---|
| `starter-only-minimal` | 낮은 둥근 돌 4개, 서로 떨어진 두 돌의 부착조류 각 1회, 중앙 틈과 양쪽 밝은 가장자리의 나사말 3포기, 두 먹이 구역에 암수 한 쌍씩 둔 새우 4마리, 식물플랑크톤·물벼룩 각 3개체, 두 균 기능군 각 2회 명시적 접종 | 숨은 초기 균막 없이 플레이어가 실제로 구성한 최소 순환계의 붕괴 |
| `full-stock-stress` | 낮은 둥근 돌 4개 각각에 두 부착조류, 중앙 틈과 양쪽 밝은 가장자리의 나사말 3포기, 두 구역에 암수 한 쌍씩 둔 새우 4마리, 식물플랑크톤·물벼룩 각 3개체, 두 균 기능군 각 2회 | 지급 자원을 많이 배치했을 때 생물 부하와 분해 부하가 커져 무너지는 문제 |

첫 구조 대조는 세로 판석 4개와 각 기둥에 한 마리씩 떨어뜨린 새우를
사용했다. 나사말 뿌리의 시작 광량이 `17.5~24.7`에 몰렸고 두 구성 모두
나사말이 사라졌다. 최소 구성은 조류 총량이 나중에 회복했는데도 새우가
`2,400초`에 절멸했고, 전체 지급 구성은 새우 `45마리`가 남았지만 후반
물벼룩 최저가 `10마리`였다. 탐색 반경을 넓혀 이 배치를 억지로 통과시키지
않고, 뿌리 사이에 밝은 틈을 남기는 낮은 둥근 돌과 먹이 접종점 옆의 암수
쌍으로 fixture를 바꿨다. 최종 장주기는 이 구조 효과와 공통 물 흐름을
따르는 새우 먹이·교미 단서 추적을 함께 측정하되, 두 단서장이 물질
장부를 바꾸지 않는 단위 대조도 별도로 실행한다.

두 시나리오는 모두 `10,800초`를 실행하고 후반 `7,200초`를 따로 판정한다.
최소 배치에만 느슨한 합격선을 주지 않는다.

- 물벼룩은 한 번 놓을 때 실제 한 개체만 생긴다. 자연번식 뒤 후반 최저
  `15마리`, 평균 `30마리`, 최종 `20마리` 이상과 후반 출생·성숙,
  창시자 교체와 살아 있는 2세대 이상 자손을 함께 확인한다. 이는 한 표본의
  `19/20` 차이를 절대 경계로 삼지 않으면서도 다음 단계에 넘길 수십 마리의
  먹이 저수량을 요구하는 통계 판정이며, 개체를 자동 보충하는 하한이 아니다.
- `1,000마리`는 게임 상한이나 번식 제한이 아니라 작은 미션 수조에서
  수천 마리로 치닫는 비정상 폭증만 잡는 검증 경보다. 관찰된 `211마리`
  파동은 정상 범위로 두며, 정상 계산에는 개체 수 하드 캡이나 자동 보충을
  두지 않는다.
- 체리새우 후반 출생·성숙, 살아 있는 출생 자손, 암수 계통과 적어도 한
  마리의 성체, 사망 원인
- 식물플랑크톤 바닥값뿐 아니라 의미 있는 고갈 뒤 회복
- 지급 나사말 소멸 뒤 러너의 러너까지 이어진 세대, 후반 생존과 최종 생체량
- 두 균 군집, 산소·독성 노폐물·유기물 안전 범위
- `120초` 표본 전체의 질소·탄소·산소 등가 최대 장부 오차

이 항목 중 하나라도 실패하면 화면상 미션 성공 여부와 무관하게 미션 7의
장기 먹이망은 미통과다. 이 밀도 검사는 물벼룩 자체의 장기 유지 조건이지
송사리 먹이 부하를 검증한 결과가 아니다. 큰 수조에서 송사리가 실제로
물벼룩을 포식하는 별도 부하 시험과도 구분한다. 미션 8 화면의 방류 준비도는
현재 물벼룩 군집을 해석해 주는 플레이 권고이며, 송사리 먹이망 장기 통과
선언이나 배치 잠금으로 사용하지 않는다.

> **역사 기록(현재 판정에 사용 금지):** 이전 고정 휴지기 모델은
> `starter-only-minimal` 후반 `57~154마리`, `full-stock-stress`

> **현재 생애 모델 결과:** `starter-only-minimal`의 후반 물벼룩은

> 살아 있는 개체는 전부 후손이었고 최대 `11세대`까지 이어졌다.

갖춘 다음 미션에서 다시 검증한다. 상세 내용은

## 4.4 미션 8 단계식 방류 먹이망 검증

> **현재 판정: 재검증 대기.** 아래 방류 절차와 단위·회귀 검사는 최신
> 구현 기준이지만, 송사리 방류 뒤 요청 장기 구간의 최종 수치는 아직
> 확정하지 않았다. 따라서 미션 8 장기 먹이망을 통과로 기록하거나 위
> 마지막 일괄 검증 표의 통과 수에 합산하지 않는다.

미션 8의 실제 플레이와 개발 fixture를 다음처럼 분리한다.

- 게임은 식물플랑크톤·큰물벼룩과 나머지 생물을 먼저 배치하고, 큰물벼룩
  후손 성체와 여러 세대가 늘어난 뒤 일시정지해 보유 송사리를 사용자가
  직접 방류하도록 안내한다.
- 보유 목록의 현재 큰물벼룩 수, 후손 성체 수와 준비도 문구는 권고다.
  송사리 카드를 잠그거나 방류 시점을 강제하지 않는다.
- 게임 계산에는 큰물벼룩 자동 보충, 개체 수 강제 하한, 송사리 자동
  방류가 없다. 개체군이 줄면 실제 출생·사망·섭식 결과를 그대로 유지한다.
- 개발 검증기가 안정 확인 뒤 일시정지하고 송사리 2마리를 배치하는 동작은
  같은 초기 상태를 반복하기 위한 테스트 자동화이며 게임 규칙이 아니다.

개발 fixture는 처음부터 송사리를 놓지 않는다. 최장 `7,200초` 안에 다음
네 조건을 동시에 만족하면 방류 안정 확인을 시작한다.

| 안정 확인 시작값 | 기준 |
|---|---:|
| 살아 있는 큰물벼룩 | `120마리` 이상 |
| 창시자가 아닌 후손 | `114마리` 이상 |
| 후손 성체 | `30마리` 이상 |
| 살아 있는 2세대 이상 후손 | `1마리` 이상 |

확인 시작 뒤 `300초` 동안 다음 개체군 하한을 계속 유지해야 한다.

| 안정 유지값 | 기준 |
|---|---:|
| 살아 있는 큰물벼룩 | `96마리` 이상 |
| 창시자가 아닌 후손 | `90마리` 이상 |
| 후손 성체 | `24마리` 이상 |
| 살아 있는 2세대 이상 후손 | `1마리` 이상 |

유지 중 한 항목이라도 내려가면 `300초` 확인을 처음부터 다시 시작한다.
이 하한을 `300초` 유지한 뒤에도 방류 시점에서 `180초` 이내에 태어난
2세대 이상 후손이 있어야 한다. 최근 출생이 아직 없으면 개체군 하한을
유지한 채 기다린다. 모두 만족할 때만 검증기가 일시정지해 암수 송사리
2마리를 후속 방류하고, 그 시점부터 요청 장기 구간을 잰다.
`120/114/30`, `96/90/24`는 개발 fixture의 재현 가능한 방류 시점이지
미션 완료 조건이나 게임 내 개체 수 보정값이 아니다.

송사리 직접 먹이는 큰물벼룩을 주식으로 하고, 실제 구조량이 삼킬 수 있을
만큼 작은 어린 체리새우만 보조식으로 허용한다. `어린 개체/성체`라는 단계
이름만으로 먹이 가능 여부를 끊지 않고 피식자의 연속적인 구조량을 본다.
식물플랑크톤, 부착 조류, 생물막과 나사말은 송사리의 직접 먹이로 인정하지
않으며, 누적 섭식 증가의 최근 먹이 표식에 금지 먹이가 하나라도 나오면
검증 실패다.

송사리의 국소 위험 단서를 받은 큰물벼룩은 성숙과 번식 배분을 바꾸는
생애사 반응을 사용한다. 그러나 위험 단서는 비물질성 정보이므로 먹이,
에너지나 번식 물질을 추가하지 않는다. 낮아진 성숙 기준도 성체 생존 구조
하한 아래로 내려가지 않으며, 한 육방의 각 새끼는 어미가 실제 섭식·동화해
보존한 번식 저장량으로 출생 구조량을 전부 지불해야 한다. 이 계약은
단서 반응 단위 시험과 탄소·질소·산소 등가 장부에서 함께 확인한다.

송사리가 없는 대조 수조에서 식물플랑크톤이 남았는데도 번식 배분이
중간 농도에서 0으로 끊기는 현상이 확인되어, 실제 국소 여과·동화 뒤에
다시 적용되던 주변 먹이 농도의 중복 곱셈 계수를 제거했다. 현재
식물플랑크톤 동화 순잉여, 어미 저장량과 완전한 새끼 질량 지불 조건은
그대로이므로 자동 증식이나 개체 수 보정은 아니다.

송사리 성체 암컷은 번식 저장량과 성체 유지분을 제외하고 알로 전환할 수
있는 저장량의 합이 한 쌍의 알 질량보다 부족할 때만 사냥을 계속한다.
화면용 에너지 값만 높다는 이유로 미지급 알을 남긴 채 사냥을 중단하지
않고, 반대로 실제 알 질량이 이미 확보되면 추가 포식을 멈춘다.

포식 압력은 발견·포획 상수만 반복해서 낮추지 않고 공간과 행동으로
분리한다. 큰물벼룩은 낮에 국소 위험 단서와 나사말 시각 차폐의 결합
경사를 따라 움직이고, 밤에는 실제 접근 중인 송사리에만 직접 도주한다.
송사리가 같은 수관 안에 들어오면 차폐 이득은 줄지만 완전히 0이 되지
않는다. 송사리는 성공한 포식 질량을 체급 비례 위 내용물 신호에 기록하고,
소화로 포만이 풀리기 전에는 성장·번식 물질 부족만으로 새 먹이 표적을
연속 획득하지 않는다. 이 신호는 이미 장부에 들어간 물질을 복제하지 않는다.
관련 국소성·야간 직접 도주·잔여 차폐·포만 표적 해제 단위 검사를 장기
fixture와 별도로 수행한다.

다음 명령은 위 단계식 방류와 송사리 식이 귀속, 모든 생물종의 후손 유지,
출생·성숙·포식, 피난 틈, 수질과 물질 장부를 한 fixture에서 실행한다.

```text
npm run verify:mission-8-food-web
```

현재는 단위·집중 회귀 결과와 별개로 기본 `10,800초` 송사리 방류 후 구간의
최종 통과 결과를 기다린다. 결과가 확정되기 전에는 더 짧은 진단 실행의
최종 마릿수나 치어 한 마리 부화를 장기 공존의 증거로 사용하지 않는다.

미션 2·3·5·6의 최종 성공 판정과 장주기 생존은 위 수동 확인에서 같은 계산을
반복하지 않고 전체 자동 회귀와 50주기 확장 검증 결과를 사용했다. 수동 확인은
지급 제한, 배치·선택·카메라·관찰·저장처럼 화면에서만 확인할 수 있는 계약에
집중했다. 이번 확인에서 새로 재현된 화면 파손, 흰 화면, 테두리 소실 또는
조작 불능 문제는 없었다.

기존 `5초` 제한의 나사말 수관 광량장 재사용 검사와 `15초` 제한의 수온 구배
검사는 전체 장주기 회귀 직후 CPU 상태에 따라 각각 약 `0.55/0.68초` 늦게
끝나 거짓 시간 초과가 발생했다. 두 검사는 벽시계 성능을 판정하지 않으므로
생태·수치 합격식은 바꾸지 않고 안전 시간만 각각 `15/30초`로 명시했다.
실제 64배속 성능 계약은 별도의 미션 4·5 장기 검사에서 계속 측정한다.

미션 4의 30,000초 자동 회귀는 평평한 바닥만 쓰지 않고 넓적한 돌과 세로 돌을 함께
배치하고, 바닥·돌 표면에 두 조류를 분산 접종해 번식시킨 뒤 성체 4마리를 방류한다.
후반 구간에서 절멸 없이 개체군이 하강·반등하고 5세대 이상 출생·성숙이 이어지며,
생산자도 섭식 뒤 감소와 회복을 보여야 한다. 새우 수는 `2,048마리` 기술 안전선에
접근하지 않아야 하고, 생산자는 총량 35를 표면별로 나눈 유한 배경 자원 범위에
머물러야 한다. 별도 무조류 회귀는 초기 저장량만으로 미션 목표를
통과했는지가 아니라 실제 먹이 수조보다 개체군이 먼저 감소하는지를 확인한다.
